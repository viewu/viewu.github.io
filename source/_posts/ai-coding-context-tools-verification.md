> 一个非技术用户的 AI Coding 协作笔记（二）

刚开始使用 AI Coding 工具时，我把它理解成一个更强的聊天机器人。

我提供问题，它给出答案；我说“帮我修改”，它返回一个看起来更好的版本。至于上下文、Tool、Skill、Agent Loop，这些词听起来更像开发者才需要理解的内部结构。

真正用 Codex 处理简历、Word、面试资料和项目文件后，我才发现：我不需要掌握模型训练，也不需要会搭建 Agent，但必须理解几件和结果直接相关的事。

它这一次看见了什么？  
它可以调用哪些能力？  
它根据什么判断下一步？  
它说“完成”时，有没有证据？

这些问题分别对应上下文、工具、工作方法和验证。理解它们以后，我才不再把每次失败都笼统归结为“模型不够聪明”或者“提示词写得不好”。

## 三个让我开始怀疑“越多越好”的现象

我先后遇到过三种情况。

第一，会话变长以后，回答不一定越来越贴近需求。

同一个窗口里先改简历，再准备面试，再解释技术概念，历史信息当然更多，但有效信息和无关信息也混在了一起。我自己都很难快速复述当前任务的边界，更不能理所当然地期待 AI 每次都抓住最重要的部分。

第二，能使用的工具更多，不代表每次都能选得更准。

读 Word、解析 PDF、联网搜索、操作浏览器、生成图片、修改文件，每一种能力都很有用。但一个任务真正需要的可能只有两三种。工具用途重叠、名字模糊或返回大量无关信息时，选择和检查都会变得更难。

第三，AI 说“已完成”，不等于产物真的可以使用。

简历文件可以成功生成，却可能出现尾部空白页；Word 正文可以完整，却可能在渲染时断字；面试总结可以写得流畅，却可能没有读取我提供的材料。

![](/images/ai-coding-context-tools-verification/2.png)

这三个现象让我意识到：AI Coding 的结果不只由“模型会不会回答”决定，还取决于信息、行动和反馈如何被组织。

## 用一个简单循环理解 Agent

Anthropic 在介绍 Agent 时，把它描述为一种由模型动态决定过程和工具使用的系统。执行过程中，Agent 会通过工具调用或代码运行获得环境反馈，再据此继续、调整或停止。[Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

如果不使用技术术语，我会把这个过程理解成：

> 获取信息 → 判断下一步 → 调用工具行动 → 检查结果 → 继续或结束

![](/images/ai-coding-context-tools-verification/3.png)

例如，我让 Codex 根据一份面试纪要生成复盘：

1. 它先读取任务要求和指定文件；
2. 判断需要提取 PDF 内容；
3. 调用工具读取 PDF；
4. 如果得到乱码，就查看结果并换成页面渲染或其他读取方式；
5. 根据真实内容生成复盘；
6. 检查文件是否写出，再告诉我保存位置。

关键并不是“它一次就想出了完美答案”，而是它能在行动后读取反馈。

这也解释了为什么环境和工具如此重要。只靠聊天，模型只能根据对话生成文字；能够读取文件、执行命令和检查产物后，它才有机会把任务推进到现实世界里。

## Context：决定它这一刻看见什么

上下文可以先粗略理解为：模型当前能够读取并用于判断的信息。

它可能包括：

- 我刚刚提出的任务；
- 当前会话的历史消息；
- 项目说明和规则；
- 已读取的文件内容；
- 工具返回的结果；
- 为当前任务加载的工作方法。

上下文并不是越多越安全。

假设我只想根据面试纪要总结失败原因，真正重要的是纪要内容、目标岗位和输出要求。如果同时塞入几份旧简历、其他公司的岗位描述、大量通用面试文章和一长串已经过时的讨论，“信息更多”很可能只是提高了筛选难度。

![](/images/ai-coding-context-tools-verification/4.png)

我的做法开始变得简单：

- 明确告诉 Codex 只读哪些资料；
- 不相关任务放到新会话；
- 长期项目提供一个短入口文件；
- 工具输出只保留判断下一步需要的部分；
- 任务结束后留下交接记录，而不是无限延长同一段对话。

OpenAI 对 Codex App 的说明提到，任务可以放在项目中的独立线程里推进和审阅。[OpenAI：Introducing the Codex app](https://openai.com/index/introducing-the-codex-app/) 对我而言，这种组织方式的价值不是多开窗口本身，而是让每个窗口有相对清楚的目标和资料范围。

上下文管理的核心不是把所有知识都交给 AI，而是让它在当前步骤看到真正需要的部分。

## Tool：决定它能够做什么

如果说上下文是“看见什么”，工具就是“能够做什么”。

一个普通聊天模型可以告诉我如何修改 Word；拥有文件工具的 Agent 可以真的生成 Word。它还可能读取 PDF、搜索网页、运行脚本、检查文件或控制浏览器。

工具给 Agent 带来行动能力，也带来新的风险。

例如，“修改简历”至少涉及读取原文件、写入新文件和检查版面。如果写入工具默认覆盖原件，或任务里没有声明版本规则，Agent 可能在技术上正确完成动作，却让用户失去旧版本。

因此，我现在看工具不只看“它能不能做到”，还看：

- 这个工具什么时候应该用？
- 哪些情况不应该用？
- 它会读取还是修改数据？
- 修改是否可逆？
- 返回结果能否支持下一步判断？
- 失败时能否给出清楚原因？

![](/images/ai-coding-context-tools-verification/5.png)

Anthropic 的 Agent 实践建议也特别强调工具接口、说明和边界。工具越相似，定义越含糊，模型越难稳定选择。[Anthropic：工具与 Agent 的接口](https://www.anthropic.com/engineering/building-effective-agents)

对普通用户来说，不一定需要亲自设计工具，但可以控制授权：先允许读取，确认计划后再允许写入；敏感文件限制范围；涉及删除、覆盖、联网和外部发布时保留人工确认。

## Skill：不是新能力，而是一套可复用的做事方法

我曾经容易把 Tool 和 Skill 混在一起。

后来我用一个很简单的区别记忆：

> Tool 让 AI 能做某个动作，Skill 告诉它这类任务应该怎样做。

读取 Word 是工具能力；“如何编辑并检查一份 Word 文档”则是一套工作方法，可能包含先提取文本、保留原件、修改格式、渲染页面、逐页检查和最终交付。

OpenAI 将 Codex Skills 描述为由说明、资源和脚本组成的工作流包，可以让 Codex按照团队偏好的方式完成特定任务。[OpenAI：Codex Skills](https://openai.com/index/introducing-the-codex-app/)

Skill 的价值是减少每次从零解释流程，但它也不应该成为什么都往里装的百科全书。

我更愿意把它理解成一张专业工作卡：

- 什么任务触发它；
- 需要读取什么；
- 按什么顺序执行；
- 哪些动作必须确认；
- 最终交付什么；
- 怎样判断通过。

当一个 Skill 同时试图负责审查、发布、调试、部署和事故处理时，它就很难保持清楚。对我自己的项目文档也是一样：入口文件只负责导航，详细资料按需读取，不把所有内容堆在同一个地方。

## Verification：决定“完成”是否可信

验证是我最晚开始重视、现在最不愿意省略的一环。

在代码任务里，验证可以是测试、类型检查、Lint 或运行结果；在我的文档任务里，它可以是：

- 目标文件是否存在；
- 正文是否包含要求的章节；
- 页数是否符合要求；
- Word 渲染后是否断字或重叠；
- 引用链接是否正确；
- 是否误改原文件；
- 输出是否真的基于指定材料。

OpenAI 在 Codex 的介绍中强调，用户可以通过日志、测试结果和引用审查代理的工作，也建议在应用修改前进行人工检查。[OpenAI：Introducing Codex](https://openai.com/index/introducing-codex/)

这给了我一个很实用的判断：

> 如果我说不清“怎样证明任务做对了”，就不适合立刻把任务完全交给 Agent。

例如，“把我的简历改好”很难验证；“生成一份一页的投递版，不覆盖原件，保留三个项目，每个项目包含行动和结果，渲染后无断字，并列出仍需我确认的数据”就清楚得多。

验证标准不一定复杂，但必须能够观察。

## Workflow 与 Agent，没有谁天然更高级

“Agent”这个词很容易让人联想到更先进、更自动、更有想象力的系统。但固定流程并不低级。

Anthropic 对两者做了一个实用区分：

- Workflow：模型和工具按照预先定义的路径执行；
- Agent：模型根据任务进展动态决定过程和工具使用。

明确、重复、风险高的任务，固定流程往往更让人放心。

例如，每次发布文章前都执行“检查标题—检查链接—检查错别字—渲染页面—确认文件”的清单，没有必要让 Agent 临场发明顺序。

而“扫描一组零散材料，判断哪些与目标岗位有关，再决定还缺什么信息”无法提前写死每一步，更适合让 Agent 动态探索。

实际任务也经常把两者混在一起：

- Agent 先调查材料并制定方案；
- 用户确认方向；
- 后续按照固定 Workflow 生成和验收；
- 遇到异常时再让 Agent 判断如何处理。

真正重要的不是贴上哪个标签，而是把确定的部分固定下来，把需要判断的部分留给模型，同时设置停止条件和人工检查点。

## 一个任务是否适合交给 Agent，我先问两个问题

现在面对一个新任务，我会先看两个维度。

### 一、目标是否清楚？

我是否能说明最终要得到什么、给谁使用、有哪些边界？

### 二、结果是否可以验证？

我是否能根据文件、数字、页面、测试、来源或清单判断它有没有做对？

由此会出现四种情况：

- **目标清楚，结果可验证**：最适合交给 Agent，例如按明确要求生成并检查一份文档。
- **目标清楚，结果难验证**：可以让 AI 提供方案，但需要专业人士或用户深入审查。
- **目标模糊，结果可验证**：先让 AI 探索和提出选项，再由人确定目标。
- **目标模糊，结果也难验证**：不宜直接追求自动完成，应该先做研究、澄清问题或建立评判标准。

这比问“AI 能不能做”更有用。

很多时候，AI 当然能够生成一个结果。困难的是：这个结果是不是我真正需要的，以及我凭什么相信它。

## 非技术用户不必理解模型内部，但要理解协作边界

我仍然不具备搭建 Agent 系统所需的工程知识，也不会因为读了几篇文章就假装自己理解大模型内部的一切。

但这不妨碍我建立一套足够实用的认识：

- Context 决定它依据哪些信息判断；
- Tool 决定它能采取哪些行动；
- Skill 提供一类任务的做事方法；
- Verification 提供完成与否的证据；
- Agent 在行动和反馈之间循环；
- 人负责目标、授权、边界和最终取舍。

这些概念的价值，不在于让我说出更多技术名词，而在于让我遇到问题时知道先检查哪里。

回答跑偏，先看资料范围和上下文。  
工具用错，先看能力是否过多或边界是否含糊。  
流程不稳定，考虑把确定步骤固化。  
声称完成却不可用，补上验收和反馈。  
任务越做越大，回到目标与停止条件。

AI Coding 不只是“帮我写东西”。它是一种会读取信息、调用工具并根据反馈继续行动的协作方式。

而普通用户真正需要学习的，也许不是如何把一切交给 AI，而是如何让每一次交付都有范围、有证据，也有回头路。
