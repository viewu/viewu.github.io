# 第一次做开发实习，我是怎么从“只会写代码”开始理解真实工程的

进入第一份开发实习之后，我最大的感受之一，是学校里所谓的“会编程”，和真正参与一个公司的软件项目，中间其实隔着很长的一段距离。

以前学习计算机，我会自然地把注意力放在语言、算法、模型这些东西上。

会不会 Python？  
知不知道某个算法？  
能不能把代码写出来？

但真正进入公司的项目以后，我发现每天遇到的问题完全不是这样排列的。

我会遇到 Git、SSH、API、端口、环境变量、Base URL、Docker、前端启动脚本、CLI、GitHub Actions、异步编程……

有时候甚至代码一行都还没有写，半天就已经过去了。

2026 年 8 月，我开始刻意把自己在实习过程中遇到的问题记录下来。回过头看，这些看起来非常零散的问题，其实慢慢拼成了一张完整的工程知识地图。

而这可能是我这段实习真正开始学到东西的地方。

---

## 一、我对 CLI 的态度发生了很大的变化

实习之前，我其实并不喜欢终端。

Claude Code 刚出来的时候，因为它主要运行在 Terminal 里，我甚至天然觉得这种方式不如带聊天窗口的 AI 编程工具舒服。

我更喜欢 Cursor、Codex 这一类看起来更直观的产品。

原因也很简单：

**GUI 看起来更容易，而 CLI 看起来像是程序员为了显得专业才使用的东西。**

但真正实习一段时间以后，我的看法几乎反过来了。

我开始发现：

```bash
git status
git pull
pnpm run dev:shop
curl ...
gh ...
claude
```

这些命令并不是“为了炫技而存在的黑窗口操作”。

它们本身就是开发环境的一部分。

<img src="/images/internship-record-02-understanding-real-engineering/2.webp" style="zoom:60%;" />

尤其开始使用 Claude Code 以后，这一点变得更加明显。

Claude Code 可以直接待在项目目录里，读取代码、执行 Git、运行测试、调用 Shell 命令、修改文件。

AI 不再只是一个和我聊天的窗口，而更像真正进入了我的开发环境。

于是我开始主动研究：

- Claude Code 的配置文件放在哪里；
- `settings.json` 到底控制什么；
- `/resume` 到底在恢复什么；
- Claude 的 session 和 Terminal 进程是什么关系；
- 多个终端为什么会看到不同的上下文；
- Claude Code 有哪些退出方式；
- Cursor、TRAE 和 Claude Code 到底应该怎么选择。

慢慢我发现，自己真正需要学习的已经不是“某个 AI 编程工具怎么用”，而是：

> **如何让 AI Agent 进入一个真实的软件工程工作流。**

这也是我现在越来越喜欢 CLI 的原因。

因为在开发环境里，很多事情最终都会回到命令。

## 二、第一次真正理解 API，是因为它坏了

以前别人问我什么是 API，我大概也能回答：

> API 是 Application Programming Interface，应用程序编程接口。

这个定义当然没有错。

但这种“知道定义”和真正理解 API，差别非常大。

让我真正开始理解 API 的，反而是一次报错。

我使用 Claude Code 时，并不是直接使用 Anthropic 的模型，而是通过 DeepSeek API。

配置中会出现几个东西：

```text
API Key
Base URL
Model
```

最开始，它们对我来说只是几个“配置项”。

能跑就行。

后来我把公司的电脑从公司带回家，Claude Code 突然报错：

```text
ConnectionRefused
```

公司的 Base URL 类似：

```text
http://192.168.x.x:xxxx
```

那时候我才真正意识到：

`192.168.x.x` 本质上是一个局域网地址。我在公司可以访问，不代表回到家还能访问。尽管以前408的时候学过计算机网络，但直到这一刻才真正对那些课本上的知识有了深刻的理解。

于是我尝试把 Base URL 改成 DeepSeek 的公网接口。

结果错误又变成了（没有把公司的API key换成自己的API key）：

```text
401 Authentication Fails
```

这两个错误看起来都是“Claude 用不了了”，但实际上完全不是同一个层级的问题。

<img src="/images/internship-record-02-understanding-real-engineering/3.webp" style="zoom:60%;" />

`ConnectionRefused` 更接近：

> 我连服务器都没有连接上。

而 `401` 则说明：

> 服务器已经收到请求了，只是不认可我的身份凭证。

这件事情给我的一个很深的体会是：

**报错信息不是一个需要被消灭的红色提示，而是系统正在告诉你问题发生在哪一层。**

以前遇到错误时，我更多是在搜索：

> “这个错误怎么解决？”

现在我会先问：

> “请求走到哪一步失败了？”

这是完全不同的排障思路。

## 三、我开始发现：配置也是代码的一部分

类似的事情后来不断出现。

API Key 应该写在哪里？`settings.json` 在哪里？Windows 和 macOS 的配置文件为什么不一样？环境变量和 JSON 配置是什么关系？公司的 API Key 能不能在两台电脑同时使用？换一个服务是不是只替换 Key 就够了？

过去我潜意识里认为：

> 写 Python、JavaScript 才叫开发。

配置文件只是一些附属工作。

但进入真实项目以后，我逐渐发现：

**一个程序能不能运行，代码只是其中一部分。**

还有：

```text
代码
↓
依赖
↓
配置
↓
环境变量
↓
网络
↓
服务
↓
权限
↓
基础设施
```

任何一层出现问题，最终表现出来都可能只是：

> “程序跑不起来。”

所以工程能力很重要的一部分，其实是判断：

**到底是哪一层坏了。**

<img src="/images/internship-record-02-understanding-real-engineering/4.webp" style="zoom:60%;" />

这也是为什么很多有经验的工程师处理问题特别快。

并不一定因为他们见过这个具体错误。

而是因为他们能够快速缩小问题范围。

## 四、GitHub 也不只是“存代码的网站”

8 月我还遇到过 GitHub CLI 的认证问题。

使用：

```bash
gh auth login
```

登录时，我粘贴了 Personal Access Token。

结果提示：

```text
missing required scope 'read:org'
```

如果是以前，我可能只会把它理解成：

> token 不对。

但现在再看，就会发现这里其实涉及的是另一个非常重要的工程概念：

**权限。**

一个 Token 并不是拿到以后就拥有全部能力。

它可以拥有不同的 scope。

比如：

```text
repo
read:org
workflow
```

不同的权限决定这个 Token 能做什么。

与此同时，我又开始接触 GitHub Actions。

以前对 GitHub 的理解基本停留在：

> GitHub = 放代码 + Git 协作。

后来才慢慢发现，一个成熟的软件仓库旁边其实还围绕着一整套自动化流程：

```text
写代码->commit->push->Pull Request->CI / GitHub Actions->自动测试->检查->合并->部署
```

<img src="/images/internship-record-02-understanding-real-engineering/5.webp" style="zoom:60%;" />

代码仓库并不是一个静态文件夹。

它本身就是整个工程流程的中心节点。

## 五、很多以前“见过”的词，我其实根本没有理解

实习还有一个很明显的作用：

它会非常诚实地暴露知识漏洞。

比如“端口”。

我以前无数次见过：

```text
localhost:3000
localhost:5173
localhost:8080
```

但真让我解释：

> 为什么需要端口？

我其实说不清楚。

后来才逐渐理解：

一台电脑只有一个 IP，但电脑上可以同时运行很多网络服务。

所以可以粗略理解为：

```text
IP 地址 → 找到哪台电脑
端口 → 找到这台电脑上的哪个程序
```

类似的还有 ORM。

ORM 全称 Object Relational Mapping。

过去看到项目里：

```python
User
Product
Order
```

这种对象，我可能只觉得：

> 这是 Python 类。

但 ORM 真正解决的问题，是：

```text
Python 世界中的对象
        ↕
关系型数据库中的表
```

程序员希望操作：

```python
user.name
```

而数据库真正存储的是：

```sql
SELECT name FROM users ...
```

ORM 就是在两种世界之间做映射。

<img src="/images/internship-record-02-understanding-real-engineering/6.webp" style="zoom:60%;" />

理解这个以后，再去读后端项目，很多代码突然就不再是孤立的语法了。

## 六、我终于决定系统补一次 Python

这是一个挺有意思的变化。

我的编程基础主要来自 C 语言。

过去遇到 Python 项目时，我一般是：

看得懂一点就继续往下看。

不会的语法再查。

这种方法在简单代码里没问题。

但进入 Agent、后端接口以及真实业务代码以后，我逐渐发现，如果连 Python 最基本的语言思想都不熟悉，阅读效率会越来越低。

比如：

```python
async def
```

以前我可能只知道：

> 这是异步函数。

但什么叫异步？为什么 Web 后端需要异步？为什么等待数据库、网络请求的时候不应该让整个线程一直阻塞？

这些问题继续向下挖，就会涉及：

```text
同步 / 异步
阻塞 / 非阻塞
协程
I/O
事件循环
```

还是一样的道理，学习408时，书本的知识迁移到真实的工程实践中，还有一段不小的距离。

于是我最终决定，不再完全依赖“碰到什么查什么”，而是系统补一遍 Python 最基础的语法和思想。

但我也没有准备重新从一本几百页的 Python 教材开始学。

我的策略变成了：

> **先掌握最小必要知识，然后继续回到项目里读真实代码。**

因为现在我越来越相信：

**编程语言不是背出来的，而是在大量阅读和使用过程中长出来的。**

## 七、我还顺便开始理解：语言只是工具

这段时间我也开始了解 Go。

以前学一门语言的时候，我容易关注：

> 它的语法长什么样？

但现在我更关心：

> 为什么工程师要创造这门语言？

Python 为什么开发快？

Go 为什么强调简单、并发和部署？

C 为什么更加贴近底层？

不同语言其实是在做不同的工程取舍。

这也是实习带给我的变化。

我的关注点正在慢慢从：

> “这个东西怎么写？”

变成：

> “这个东西为什么会存在？”

这是我觉得非常重要的一步。

如果让我在实习开始之前列一个学习清单，可能会变成：

```text
先学 Git
再学 Linux
再学 Python
再学 Docker
再学网络
再学数据库
再学 FastAPI
再学前端
```

然后三个月过去，项目可能还没有开始。

<img src="/images/internship-record-02-understanding-real-engineering/7.webp" style="zoom:60%;" />

真实的实习经历让我越来越认可另一种学习方式：

> **先进入真实问题，再围绕问题补知识。**

例如：

Claude 连不上。

于是我学习：

```text
Base URL
IP
端口
API Key
HTTP 状态码
```

GitHub CLI 登录失败。

于是我学习：

```text
Token
Scope
权限
GitHub Actions
```

项目代码看不懂。

于是我补：

```text
Python
async
ORM
```

Agent 工具越来越多。

于是我开始比较：

```text
Cursor
TRAE
Claude Code
CLI
```

每一次问题都像在知识地图上点亮一个节点。

而节点越来越多以后，它们开始互相连接。

## 九、真正的工程能力，可能就是不断建立这些连接

刚实习的时候，我经常觉得自己什么都不会。

看到一个陌生名词，就觉得又出现了一个新的知识点。

但现在回头看，我发现很多问题其实属于同一张图。

比如：

```text
Claude Code
    ↓
终端 CLI
    ↓
Shell
    ↓
环境变量
    ↓
API 配置
    ↓
HTTP 请求
    ↓
端口 / 网络
```

另一边：

```text
Git
 ↓
GitHub / GitLab
 ↓
Token / SSH
 ↓
权限
 ↓
CI/CD
 ↓
GitHub Actions
```

再另一边：

```text
Python
 ↓
async
 ↓
Web Backend
 ↓
API
 ↓
ORM
 ↓
Database
```

以前它们在我的脑子里是一个个独立的名词。

现在它们逐渐开始连接。

我觉得这可能就是所谓的“工程经验”。

工程经验并不是：

> 我背过多少框架。

而是当一个问题出现时，我知道：

> 它大概位于整个系统的哪个位置。

## 十、AI 时代，真正需要学习的可能反而更多了

我最近还有一个越来越强烈的感受。

AI 编程工具确实把很多工作的门槛降低了。

以前不知道怎么写的代码，现在可以直接让 Claude 生成。

不知道一个报错，也可以直接问 AI。

从这个意义上来说，编程确实变简单了。

但对于真正想成为专业开发者的人来说，AI 并没有让学习变得不重要。

恰恰相反。

因为 AI 可以一分钟生成几百行代码以后，真正稀缺的能力逐渐变成：

**你知不知道它生成的东西在做什么。**

你需要知道：

为什么这个服务需要这个端口？

为什么这里是异步？

为什么要使用 ORM？

为什么接口返回 401？

为什么换了网络以后连接失败？

为什么这个 Token 缺少权限？

为什么 Claude 修改的代码不能直接相信？

AI 可以帮我快速完成“怎么做”。

但“为什么这样做”和“出了问题应该从哪里开始找”，仍然需要自己理解。

## 写在最后

实习开始以后，我其实一直处于一种很明显的状态：

每天都很忙。

每天都在接触新的东西。

但有时候晚上回去又会觉得：

> 我今天真的成长了吗？

现在再回头看八月过半留下来的这些问题，我的答案开始变得明确了一点。

成长并不一定表现为：

> 今天学会了一个完整的框架。

很多时候，它表现为：

以前我看到：

```text
401
```

只知道“程序报错了”。

现在我知道这是认证问题。

以前看到：

```text
localhost:5173
```

觉得只是一串地址。

现在知道 IP、Host 和 Port 分别在做什么。

以前看到：

```python
async def
```

只知道这是 Python 的一种写法。

现在会继续思考它为什么存在。

以前我害怕终端，现在我反而觉得 CLI 是最高效的工程交互方式之一。

这些变化单独看都很小，但它们正在慢慢连接成一个系统。

而我现在越来越觉得：

**第一次实习真正重要的，并不是证明自己已经会多少东西。**

而是第一次进入一个真实的工程世界之后，开始知道——

**自己接下来到底应该学什么。**
