实习记录 01：项目跑起来以后，我才发现自己还没读懂代码

发表于 2026-08-01 分类于 工作 本文字数： 3.2k 阅读时长 ≈ 3 分钟
实习第一周的工程环境、代码阅读、AI 辅助与能力边界复盘。

实习记录 01：项目跑起来以后，我才发现自己还没读懂代码

这份实习是在暑假开始以后才找到的。

暑假前，我急急忙忙投了很多简历，最后大多石沉大海。那段时间越投越着急，总觉得应该尽快抓住一个机会。后来我稍微佛系了一点，想着一边继续投简历，一边补自己的能力，反倒在这个时候收到了实习机会。

所以刚入职时，我除了紧张，也有一种终于落地的满足感。和我一起入职的还有另外三位小伙伴，其中一位后来还给我们投喂了酸奶。第一周虽然大部分时间都在配置环境、读项目和处理问题，身边这些很小的善意，也让我慢慢放松下来。

实习第一周，我花了五天时间让一个现有项目在本地运行起来。

周一刚接触项目时，我对“跑起来”的理解还很简单。拿到代码，安装依赖，执行启动命令，接下来应该就能读代码、改功能了。实际操作以后才发现，代码只是其中一部分。开发环境、依赖服务、访问权限、前后端配置和网络连接，任何一处没接上，项目都可能停在启动之前。

这五天里，我问了很多基础问题。Docker 为什么拉取失败，SSH Key 在验证什么，前端脚本为什么通过 pnpm 启动，curl 能帮我看到什么，后端接口、缓存、搜索服务和配置服务分别处在什么位置。单独看，每个问题都很零散。等项目终于在本地正常运行，我才稍微看清，它们都属于同一套工程环境。

不过，项目能够运行，和我能够读懂项目，中间还有一段很长的距离。

我先学会了判断问题卡在哪一层

第一周最直接的收获，是我开始把报错分层。

下载或拉取失败时，我会先看网络、代理和镜像源；终端找不到命令时，我会检查安装位置和 PATH；仓库无法访问时，我会检查账号权限和 SSH 配置；服务启动后接口仍然不通，再继续看端口、环境变量和依赖服务。

以前看到最后一行红字，我很容易直接怀疑代码写错了，然后跟着搜索结果不断换命令。现在我会先问一句：当前错误发生在网络、环境、权限、依赖、接口，还是业务逻辑？

这个判断仍然需要依赖搜索和 AI 帮助，但至少让我少了一些毫无方向的尝试。curl 也不再只是安装命令里偶尔出现的词。它是一个可以在终端里发送网络请求、查看响应的工具。理解这一点以后，我再看到连接超时，就知道应该先检查网络链路，而不是立刻去改项目代码。

代码来源也从下载压缩包变成了 Git 仓库。压缩包能让我查看一份代码，却无法自然地同步团队更新。通过 Git 获取仓库、拉取最新代码、在自己的分支修改、查看差异，再提交给团队审查，这才是团队项目持续变化时需要的协作方式。

第一周里，我已经把项目跑了起来，也能解释一部分环境问题。到了代码内部，我的理解很快又变得模糊。

Claude Code 带我走了一遍，我还不能独立走一遍

项目运行后，我借助 Claude Code 追过一次请求链路。

它可以从前端入口开始，告诉我请求发到哪里，后端由哪个模块接收，后续又经过哪些处理，结果最后怎样回到页面。顺着它给出的文件、函数和调用关系，我大概知道了各个模块的功能，也第一次看到一次用户操作会经过这么多层。

但这次追踪主要由 AI 带着完成。我没有独立找到入口，也没有靠自己把每一段调用关系串起来。阅读代码时，我能看懂局部说明；一旦深入到状态怎样变化、函数为什么这样调用、某个处理为什么放在这里，我就很难继续判断。

AI 可以很快画出一条调用链，我目前还缺少验证这条链的能力。

这个差距很容易被“我已经看过代码”掩盖。Claude Code 给出的解释足够清楚时，我会产生一种已经理解项目的感觉。可这里的“理解”大多停留在模块负责什么。让我自己解释具体实现，或者修改其中一段逻辑，我很快就会暴露出断点。

这也让我想起之前看过的许多计算机学习视频。我一直知道自己欠缺实践经验，但进入项目以后，我才切身体会到这种“欠缺”带来的压力。视频里的代码能看懂，概念也能跟着说出来，轮到自己定位问题、解释调用关系和判断改动影响时，原来模糊的不足一下子变得具体了。

从“看会”到“学会”，再到能够独立处理问题，中间还有很长的一段路要摸爬滚打。

SSE 和 LangGraph 让我补上了两块浅层认知

这一周，我花了不少时间理解流式返回。

AI 回答逐段出现在页面上，看起来只是文字不断增加。落到工程里，后端需要持续产生数据，传输层需要把数据送给前端，前端还要解析数据并更新同一条消息。SSE 处理的是服务器怎样把连续结果传给前端。

后来我继续了解 LangGraph，才知道它处理的是另一层问题。一个任务可以被拆成多个节点，节点之间通过边连接，State 保存执行过程中的数据。节点可以调用模型，也可以查询数据、执行普通代码或调用工具。流程如果包含动态判断、工具选择和循环，便可以用来组织 Agent。

我目前能说清的关系很有限：LangGraph 负责后端任务怎样编排和执行，SSE 负责持续产生的结果怎样传到前端，页面再负责把结果显示出来。

这套解释帮我看见了项目的大致结构，却还没有让我读懂具体代码。每个节点更新了哪些状态，流式事件从哪里产生，数据格式怎样转换，前端收到以后怎样更新页面，我仍然需要依赖 AI 的说明。

一次没有效果的修改，把理解缺口暴露了出来

这一周最值得记录的经历，是我在 AI 帮助下修改了一处流式返回功能。

修改只在本地尝试。运行后，它增加了额外开销，最终效果却没有改善。我随后撤回了这次修改。

如果只看操作过程，我完成了定位、修改、运行和对比。但我当时并没有充分理解项目原有的流式逻辑，也无法在改动前准确判断新增处理会落在哪个环节、为什么可能增加开销。AI 能生成一份看起来合理的修改，我却缺少足够的代码理解去判断它是否符合现有实现。

直到我继续了解项目里的 LangGraph 编排，才大概明白流式结果从哪里产生，以及它和前端接收之间是什么关系。这个理解仍然比较表面，但至少让我知道，局部修改不能只盯着最后的页面效果。上游的节点执行、状态更新和事件生成方式都会影响成本与结果。

这次本地实验没有给项目带来改进，却准确暴露了我当前的能力边界。

第一周的进度，应该写得诚实一点

如果只列名词，这一周看起来学了很多：Docker、Git、SSH、pnpm、curl、API、SSE、LangGraph，还有前后端之间的调用关系。

我现在不太愿意把它们都写成“已经掌握”。

项目能够在本地运行，我完成了第一步。借助 AI 走过一遍请求链，我对项目结构有了初步认识。读过流式返回和 LangGraph 相关代码，我能解释它们大概负责什么。到了独立追踪、理解具体实现、判断修改影响和完成可靠交付，我仍然缺少足够的经验。

这一周也让我重新校准了对 AI 编程工具的期待。它能帮我搜索文件、解释概念、整理调用关系，也能很快生成修改。如果我没有能力验证，清楚的解释和完整的代码就会制造一种进展很快的感觉。那次没有效果的流式修改，刚好把这种错觉戳破了。

这一周里，技术 Leader 也给了我很多帮助。他很耐心，技术能力很强，相处时却没有什么架子。有一次我看了很久都没解决的问题，他接手后不到一分钟就劈里啪啦处理完了。那一刻我很直观地感受到，专业能力过硬的人解决问题是什么样子。

他也有过一点小小的 push。我能理解，他希望我尽快进入工作状态。后来的进展也证明，这点压力确实推着我往前走了一段。整个过程没有让我觉得难受，反倒让我更想跟上团队的节奏。

第一周结束时，我至少把“项目跑起来”和“我读懂了项目”分开了。前者已经完成，后者刚刚开始。这个判断可能不算亮眼，但比把询问过的技术都写进“已掌握”更接近我现在的位置。

能在暑假里找到这份实习，我觉得很幸运，也很满足。我希望自己以后也能成为技术 Leader 那样的人，专业技能过硬，同时让身边的人相处起来很舒服。接下来，我还要继续补上实践经验，尽量跟上团队的工作节奏，希望这段实习最后能够带给我一次看得见的个人成长。

这一周遇到的人都很好。也希望大家都能在自己的路上顺顺利利。
